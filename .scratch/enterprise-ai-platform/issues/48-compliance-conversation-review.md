# 48 — 对话记录的合规只读查阅

**What to build:** `docs/DESIGN.md` 给了 compliance 一个明确的只读职责：*只读审计日志、只读对话记录（留痕）、RoPA；不能改业务数据*（§4 角色表），并且 §5.3 在否掉 LangSmith 自托管时把这件事当作已定事实：**员工对话内容只有 compliance 可查**。票据 34 只把会话给了它的所有者（`GET /answers/conversations/{id}` 按 user_id 过滤，别人的会话与不存在同答 404），所以今天没有任何角色能履行这条职责——这一条设计决策没有归属票据，本票补上。

**Blocked by:** 34 — 流式回答、强制引用与拒答（会话与消息表由它建立）

**Status:** ready-for-agent

- [ ] 新增目录权限 `conversation.read_all`，角色**只有 compliance**；admin、hr、manager 都被拒绝（理由：§4 角色表把"对话记录"单列给 compliance，而不是给管理员；管理员的权限是账号与角色，不是读别人的提问）
- [ ] 提供只读清单与详情：按员工、按时间范围分页查阅会话与消息；**不提供**跨员工的全文本检索（会把"留痕"变成"搜索所有人的提问"，且让接口成为存在性预言机）
- [ ] 只读是**真的只读**：compliance 不能删除、重命名、续期或导出他人会话；所有者对自己的会话的删除权不受影响（D18：用户可自行删除）
- [ ] 每次查阅写审计（谁在何时读了谁的哪个会话），审计内容**不含**对话正文（正文已经在库里，审计只记主体与对象；与 D24 的追加式审计表一致）
- [ ] 留存期照旧生效：超过 90 天被清除的会话对 compliance 同样不存在（D18：90 天自动清除）
- [ ] 行级安全策略同时覆盖：compliance 的读取在**数据库层**也被允许，其他角色的读取在数据库层被拒绝（D32 的第二道防线），按 `api/tests/test_database_security.py` 的方式断言数据库自己的拒绝
- [ ] 测试：compliance 可读、其余角色 403 且在响应中完全不存在、所有者的删除权仍然生效、每次查阅有审计、超期会话不可见；越权断言针对**命中集合**而不是"标记为不可见"
- [ ] 界面不在本票范围内（`frontend-design-system.md` §8.1 没有把这一屏列入落地表）；接口契约写在票据里，供后续需要时再开前端票

## 边界

- 复用现有审计写入（`app/audit.py`）与会话/消息表（票据 34 的迁移），不新建平行表。
- 不改变票据 34 已定的所有者语义；本票只**增加**一个角色的读取面。
- `message_key`、错误码按既有约定：`ERR_<DOMAIN>_<NNN>` + `api/app/core/messages.py` 的西/英双语条目；需要前端新增的 key 在实现说明里列出（`web/` 由父代理统一补，避免与前端工作冲突）。
