# 53 — 审批界面（经理）：内联操作、驳回必填理由、申请人的依据

**What to build:** `docs/architecture/frontend-design-system.md` §6.4 用四条规则描述了一个界面：
一体处理多条的效率优先、**列表内联操作**而不必逐条进详情页；每条一眼看到谁 / 什么类型 / 什么日期 /
多少天或多少小时；审批意见可选但**驳回时必填**；显示申请人的**剩余额度与异常历史**让审批人有判断依据。
同一节的开头写的是「本系统有四个"填错代价高"的界面」——它把审批界面当作**已经存在的四个界面之一**。
但 §8.1 的"落地票据"表里没有它：`16`（审批引擎）与 `17`（人事变更）都只做了后端，`24`/`25`/`28`
的清单里与审批有关的部分也是后端。于是今天**审批人无法在本系统里做决定**——引擎能跑，界面没有。
本票补上这个界面，它是 §8.1 落地表的补漏，而不是新增需求。

**Blocked by:** 16 — 审批引擎内核与状态机（决定与状态由它算）；24、25、28、40 — 产生待办的那几条流程

**Status:** ready-for-agent

- [ ] 待办队列：列出当前调用者有权决定的审批（第 1 级为直属经理，第 2 级为人力资源），默认按**等待时长**排序，
      一次能看到多条
- [ ] **列表内联操作**：批准 / 驳回 / 退回可直接在行内完成，不必逐条打开详情页；批量操作可选，
      但**每一次决定仍是一次显式点击**（不接受"全选后一键批准"这种把审阅变成盲签的形态）
- [ ] 每条一眼可见：申请人、类型（请假 / 补卡 / 工时表 / 人事变更 / 助手草稿）、涉及日期或期间、
      数量（天 / 小时 / 分钟），以及当前处于哪一级
- [ ] **驳回必须填理由**（前端校验 + 后端仍以 422 拒绝空理由；两侧都要有，因为客户端可以被绕过）；
      批准的理由可选。理由在申请表与通知里对申请人可见
- [ ] 决定时展示**申请人的依据**：剩余年假额度、该期间的异常记录（缺卡 / 迟到 / 未完成），
      数据来自既有接口；**不在此界面重算**任何额度或异常
- [ ] 决定提交后立即从队列消失（乐观或重取皆可，但**不得**留下一个已被决定的幽灵行），
      失败时给出可操作的双语提示并保留用户在界面的输入
- [ ] 空队列 / 加载 / 错误 / 无权限四态齐备；没有待办时说明"当前没有需要你处理的申请"，
      而不是一个空表格
- [ ] **透明度**：助手起草、由本人确认的单据在此界面带标注（DESIGN §6.3 第 3 条的
      `initiated_by='agent'`）；标注来自接口字段，不是客户端的猜测。该字段由票据 41 落到接口上，
      本票负责显示——若 41 尚未完成，先把这条标为待补并写在实现说明里，不要自行发明字段
- [ ] 审批人**无法也不需要**区分来源的其他部分：金额、时长、额度、附件等与手工提交完全一致
- [ ] 西/英双语；数字与日期按界面语言格式化（设计系统 §3.3）；移动端触控目标 ≥ 44px
- [ ] `npm run visual` 覆盖本屏（队列、内联决定、驳回必填、依据面板），两种语言 × 320/768/1280，
      截图人看过并报告看到的问题——前几个前端票据都是这样发现真缺陷的

## 边界

- 不复写审批规则：谁能决定、几级、什么状态可决定，全部问引擎（`app/domain/approval/`），
  本票只负责"把引擎的答案画出来并让人点得动"
- 不做"替别人决定"：调用者的身份来自会话，界面不提供选择审批人的控件
- 不新增后端规则；若发现某条展示所需的数据接口不存在，**先加只读接口并在实现说明里写明**，
  不要在前端拼凑两个接口的结果去推断一条规则
