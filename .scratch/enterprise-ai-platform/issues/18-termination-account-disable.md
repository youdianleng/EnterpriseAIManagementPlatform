# 18 — 离职生效与账号禁用

**What to build:** 离职单在生效日当天自动完成收尾：账号被禁用、登录会话被立即清掉、员工状态改为已离职，但**历史记录一律保留不动**（工时与薪酬有法定留存期，不能因为人走了就删）。

**Blocked by:** 17 — 人员变动单：入转调离

**Status:** done

- [x] 生效日当天：账号被禁用、员工状态变更为已离职、该账号在 Redis 中的全部会话被删除
- [x] 被禁用的账号即使凭证正确也无法登录，提示为可读的西/英文案（不暴露"该用户存在"之外的信息）
- [x] 该员工的考勤、工时、请假、薪酬、工资单、审批历史**全部保留且可查**
- [x] 离职员工不再出现在通讯录、部门人数统计、可选审批人列表中
- [x] 离职员工不能被重新创建账号；如需返聘，必须通过新的入职变动单恢复（行为需明确并测试）
- [x] 若离职员工是某人的审批上级，系统提示人力资源需要为受影响的下属重新指派上级，并在重新指派前阻止相关单据提交（或自动回退到上级的上级，二者择一并在文档中写明）
- [x] 上述所有动作写入审计日志

## 实现记录

代码：`api/tests/test_termination.py`（13 项）；生效逻辑在
`api/app/domain/personnel/service.py` 的 `_finish_account`，审批人缺口的判定在
`api/app/domain/personnel/approver_coverage.py`，用人话讲就是"路线指向已经离开的人时，
拒绝而不是替代"。定时任务 `python -m app.jobs.apply_personnel_changes` 每跑一轮就把这份
缺口名单打到错误日志里（`approver_terminated`）。

**第 6 条选了"阻止提交"，不是"自动回退"。** 理由写在 `approver_coverage.py` 的模块
docstring：两级审批 + 一百人的公司里，"上级的上级"要么落到部门负责人、要么落到 HR；
HR 是二级角色而不是一条路线，替代一级等于换了一条路线，而引擎自己已经明确拒绝这样做
（请求人是自己上级时记 `skipped` 而不是转给别人）。回退还会把没人修的配置藏起来，
拒绝则在下单当天就告诉 HR 要改谁——拒绝信息里点名到人。

**第一次实现里被删掉的东西**：一开始想用"新员工沿用了离职者的邮箱"来拦住返聘，
但目录的邮箱唯一索引让这个前提基本不可达（HR 得先改离职者邮箱才能复用），于是换成
真正可达、也真正是漏洞的那一个：**把离职者的账号重新启用**。`set_active(is_active=True)`
现在会检查在职状态，拒绝并指向入职单。

### 今天能断言的历史 vs. 以后各票要补的

`test_nothing_historical_is_deleted` 断言"今天存在的每一行都还在"：员工行、**包括已结束的**
任职记录、离职单及其 payload、审批产生的通知、审计记录，以及登录身份本身——它是被禁用而
不是被删除，因为审计记录指向它。

以下表还不存在，因此只能记录而不能断言；**每一票把行加进同一个测试即可，不需要新规则**：

| 请假记录 | 22 |
| 工时/工时表 | 23–25 |
| 薪酬记录 | 43 |

### 没有测到的部分

- **真实浏览器**：会话失效是在 HTTP 层断言的（持有 cookie 的客户端下一个请求得到 401），
  没有跑前端。
- **第二级审批人离职**：二级是"持有 hr 角色的人"，没有具名审批人，因此不存在"路线指向离职者"
  的问题——这一点由 `approval_hr_unavailable` 覆盖，本票没有重复测。
- **通知发送**：离职不会给 HR 发通知（避免动 `domain/notification/`），缺口只进日志；
  员工自己的通知中心里原有记录保持可读（已断言）。
- **中途手动禁用过的账号**：`_finish_account` 对已禁用账号不再重复禁用、不再抬 epoch，
  应用记录里写 `account_disabled: false`；这条分支没有单独测（`is_active` 守卫的意图
  已由"账号不存在"那一条覆盖）。
