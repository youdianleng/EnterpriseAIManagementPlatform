# 51 — 对话留存清扫：90 天到期后真正删除

**What to build:** D18 的前半句是「90 天自动清除」。今天只有后半句成立：票据 34 在
`rag_conversations` 上写了 `expires_at = created_at + 90 天`，并**刻意不含任何 DELETE**
（它自己写明"留存清扫是后续工单的"）；票据 37 只要求界面**告知**这个期限；票据 48 假定
"超过 90 天被清除的会话对 compliance 同样不存在"。于是 `expires_at` 这一列今天没有任何读者，
到期数据永远不会消失——一条明确的留存承诺没有实现。本票补上它。

**Blocked by:** 34 — 流式回答、强制引用与拒答（`rag_conversations`/`rag_messages` 由它建立）；
50 — worker 服务（清扫要有地方按日跑）

**Status:** ready-for-agent

- [ ] 一个任务（`api/app/jobs/` 里的既有形状）删除到期的会话：`expires_at < now()` 的
      `rag_conversations` 及其 `rag_messages`（外键已是 `ON DELETE CASCADE`，但**删多少要有数**：
      返回值/日志要给出本次删除的会话数与消息数）
- [ ] **删除用的是有权删除的连接，而不是请求角色。** 迁移 0024 把 `DELETE` 从 `eam_app` 收回，理由
      是"请求路径不该删证据"；留存清扫不是请求路径，所以它需要自己的凭据（owner 连接，或一个
      `SECURITY DEFINER` 函数，或专门授予 DELETE 的角色——三选一并在实现说明里写明理由）。
      **验证要同时证明两件事**：清扫能删，而请求角色仍然不能删
- [ ] 用户主动删除（`deleted_by_user = true`）与到期删除的关系写清楚：标记是"本人立刻看不到"，
      行什么时候真正消失、是否更早被清扫，实现里要有一个明确答案，并让票据 37 的"删除是即时的"
      与它一致（界面语义 = 立刻不可见，就足够了；不要承诺行已物理删除）
- [ ] 按日跑，且**幂等**：重复运行不会删掉不该删的、不会报错、不会把已经删掉的当异常
- [ ] 审计：每次清扫写一条（删除数量与时间），**不含任何对话正文**（D24 的追加式审计表；
      正文已经不在库里了，审计只记主体与计数）
- [ ] 时钟是**数据库时钟**（`now()`），不是进程时钟：容器与时区漂移不该决定谁的数据被删
- [ ] 测试：过期的会话消失（消息一并消失）、未过期的分毫不动、边界（正好到期）有明确断言、
      重复运行安全、请求角色的 DELETE 仍被数据库拒绝、审计有记录
- [ ] 与票据 50 的关系：清扫由 worker 按日调用；worker 的循环里加它，不要另外再起一套调度

## 边界

- 不改变 D18 的 90 天，也不把它做成"可配置的留存策略"（那是票据 47 的 `retention_policies`
  数据表达；本票只实现这一个类别，若 47 想要由数据驱动，那是 47 的工单）。
- 不删除审计日志与工资单等其他类别——本票只做对话。
- 不新增表、不改票据 34 的列；若需要索引来让清扫不扫全表，`ix_rag_conversations_expires`
  已经在那里（票据 34 建它就是为了这个）。
