# 52 — 约束 B 的第 2、3 层：AI 路径的只读上下文与只读数据库角色

**What to build:** `docs/architecture/codebase-design.md` §6 的约束 B（「AI 模块不持有写仓储」）写的是**三层防御**，
并逐层说明理由：「三层都在，是因为前两层都在应用代码里，而应用代码会被人改。第三层不依赖应用代码的正确性」。
今天只有**第 1 层**有归属：票据 38 把 `ToolKind` 做成没有 `WRITE` 成员，票据 40 负责结构层的断言
（AI 可触达的工具集合里没有任何写库工具）。**第 2 层与第 3 层没有任何票据承接**——38 号工单的实现说明只写了
「只读数据库角色随后」，却没有说随后是哪张票。本票补上这两层。

**Blocked by:** 40 — 草稿工具（约束 B 的第 1 层与草稿路径由它建立）

**Status:** ready-for-agent

## 第 2 层：运行时只读上下文

- [ ] 存在一个**只读数据库会话上下文**：进入该上下文后，任何 `INSERT`/`UPDATE`/`DELETE`（以及等价的 ORM
      flush）**抛异常**，而不是静默成功或依赖调用方自觉
- [ ] AI 的请求路径（图的一次运行）**一律在该上下文中开启事务**；草稿与只读工具都在里面跑
- [ ] 有一个测试证明它在真实数据库上生效：在只读上下文里尝试一次真实写入，断言它失败，并且**表里没有多出行**
      （只断言抛异常不够——异常可能来自别处）
- [ ] 该上下文**不削弱既有规则**：RLS、`FilterSpec` 前置过滤（约束 C）仍然照常生效；本层是"再加一道"，
      不是"换一道"
- [ ] 说明并测试边界：**确认提交**（票据 41 的路径）显然要写库，因此它必须**离开**只读上下文，
      以员工本人的名义、经过既有服务层写入——而不是让只读上下文开个口子

## 第 3 层：只读数据库角色

- [ ] 存在一个**只读数据库角色**（例如 `eam_ai_ro`），它对业务表只有 `SELECT`：迁移里显式授 `SELECT`、
      **不**授 `INSERT`/`UPDATE`/`DELETE`，并且不要被 migration 0007 的 `ALTER DEFAULT PRIVILEGES` 顺带授权
      （那条默认权限是既有事实，必须显式撤销，否则这层是纸面的）
- [ ] AI 路径使用该角色连接（独立的引擎/连接串，来自设置，例如 `AI_DATABASE_URL`），**而不是** `APP_DATABASE_URL`
- [ ] 有一个测试**以该角色**运行真实的写语句并断言数据库拒绝（`permission denied for table …`），
      按 `api/tests/test_database_security.py` 的风格：断言的是**数据库自己的拒绝**，不是应用层的行为
- [ ] 有一个测试断言只读角色**仍然能读**它该读的东西（否则"全拒绝"也能让上一条通过）
- [ ] 角色命名、授权范围与密码来源写进 README 的权限一节；密码走 compose 环境变量，与既有两个角色同一套约定

## 边界

- 不改 `eam_app`（请求角色）与 owner 的既有权限；本票只**新增**一个更窄的角色与一条连接路径。
- 不把 AI 路径的读操作从 RLS 里豁免：只读角色同样受策略约束，`app.*` 上下文照常发布。
- 第 1 层（结构层）不是本票的：它是票据 40 的断言。本票完成后，三层都各有一张票、各有一组测试。
- 若实现发现"图的一次运行"与"确认提交"在同一个事务里无法拆开，**先改设计文档再改代码**：把这条偏离写进
  `docs/DESIGN.md` §10（含理由），而不是让只读上下文名存实亡。
