feat(auth): login, server-side sessions and the forced password change

Ticket 10. The session id travels in an httpOnly cookie and everything that
decides access stays on the server.

- Redis-backed sessions: `session:<id>` for the record and `session:user:<id>`
  for that user's live ids. The index is why a password change can end sessions
  on other devices without scanning the keyspace.
- Revocation is a comparison, not a scan. A session carries the epoch it was
  issued under; a password change, an administrative reset or a deactivation
  moves the account's epoch past it, so every older session stops matching.
- The forced-change gate is an application-level dependency, not a per-route one.
  A route added later cannot be accidentally exempt — which is the failure mode
  the requirement exists to prevent. Only the change-password endpoint and the
  two that explain why everything else is refused stay reachable.
- Changing a password keeps the device that made the change signed in by issuing
  a replacement session, and ends every other one. Signing the user out of the
  device they are holding would be hostile; leaving the others alive would defeat
  the point.
- Lockout after five failures, counting per account rather than per address: an
  attacker who moves between addresses would slip past an address-keyed counter.
  It fails open when Redis is unreachable, because a cache outage must not lock
  every account out of the system.
- Every outcome is audited, failures included, with the client address. A trail
  of successes only cannot answer "was somebody trying to get in".

Six defects fixed while verifying. The serious one: `conftest` used `setdefault`
on DATABASE_URL, which the container already exports, so a full test run wrote
181 audit rows into the development database — and an existing test asserted
that arrangement as expected behaviour. The others: four missing error-code
aliases that surfaced as AttributeErrors inside 500s; a duplicated enum member
and a duplicated message key; three different naming conventions across the
alias classes; and a guard that opened its own session and so could not see what
the route saw.
