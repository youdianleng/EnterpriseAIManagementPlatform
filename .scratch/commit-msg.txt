feat(org): department tree with ltree ancestry and depth rules

Ticket 06. First domain module, and it sets the layering the rest follow:
domain/ holds the rules and depends on a Protocol, repositories/ holds the SQL,
api/v1/ holds the transport.

- departments table with an ltree materialised path and a denormalised depth.
  "This department and all its descendants" is one indexed `<@` comparison
  instead of a recursive walk, which matters because the permission kernel asks
  it on nearly every request.
- Paths are derived, never client-supplied. Codes are sanitised into ltree
  labels by doubling underscores and mapping anything else to `_`, which keeps
  `r-d` and `r_d` distinct.
- Code uniqueness is a partial unique index on (parent_id, code) WHERE
  is_active: a code belongs to a position in the tree, and a deactivated
  department should not reserve it forever.
- A move rewrites the moved node and every descendant in a single UPDATE using
  subpath(), rather than one statement per row.
- Rules enforced in the domain: code taken, parent missing or inactive, depth
  limit, move into own descendant, delete with children, delete with staff.
  Errors carry a code; deciding that a code becomes a 409 is the edge's job.
- Structure cache invalidates by bumping an org:tree:version stamp in Redis
  rather than waiting for a TTL.
- Writes require a structure role and deny by default; reads stay open until
  authentication lands in ticket 11.

Depth limit: MAX_DEPTH = 4 (depths 0..4) follows the "4 层嵌套" wording in
tickets 22 and 43. Ticket 03's "部门 4 层" is a scale baseline, not tree depth.

Five defects found while verifying: a lookaround regex that matched inside its
own replacement; an in-memory substitute that dropped a path separator the SQL
kept; subtree_height counting from the root rather than the node; a `>=` where
`>` was meant; and the lru_cached engine/Redis clients being bound to the first
test's event loop, which turned /ready into a 503 in later tests.
