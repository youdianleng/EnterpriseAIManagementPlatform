feat(db): migrations, pgvector schema and real Redis wiring

Ticket 04. Establishes the migration channel every later table goes through,
and pins the two schema decisions that are expensive to reverse.

- Alembic wired to application settings rather than alembic.ini, so a migration
  run can never target a different database than the app. ALEMBIC_DATABASE_URL
  overrides it, which is how tests migrate eam_test without touching config.
- Migration 0001 creates the vector and ltree extensions and a throwaway
  _vector_smoke table carrying the locked 1536-dimension column and its HNSW
  cosine index. It creates no business tables on purpose: those arrive with the
  tickets that build their behaviour.
- app/core/constants.py holds EMBEDDING_DIMENSIONS. The migration keeps a
  literal so it always describes what it applied, and a test asserts the two
  agree — a pgvector column's dimension is schema, so drift would only surface
  as a runtime insert failure.
- app/db.py: lazy engine and session factory, get_session as the single place
  the connect/rollback/close lifecycle lives. That is what later makes the RLS
  context a one-line insertion rather than something every call site remembers.
- app/cache.py and a lifespan that disposes the engine and closes Redis.
- /ready now executes SELECT 1 against the pooled engine and pings Redis,
  instead of reporting a configured DSN.
- Tests run against a real PostgreSQL (eam_test, separate from development) with
  an outer transaction rolled back per test, plus a real Redis flushed per test.

Measurement corrected a design decision: the doc claimed 3072 dimensions only
cost index memory. In fact pgvector caps HNSW at 2000 dimensions for `vector`
and 4000 for `halfvec`, so `vector(3072)` cannot be indexed at all. Measured on
10k chunks, vector(1536) costs 95.5 MB / 0.9s index / 0.27ms query versus
halfvec(3072) at 152.6 MB / 1.8s / 0.31ms. Chose vector(1536) and rewrote
docs/DESIGN.md section 10.3; the probe stays in the repo to be re-run.
