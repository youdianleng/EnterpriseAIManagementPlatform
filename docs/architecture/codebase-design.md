# 代码组织与模块设计（规范）

> 由 `codebase-design` skill 的词汇与原则驱动。**本文档不是描述现状，而是规定代码落位**。
> 与 `docs/DESIGN.md` 的关系：DESIGN.md 回答"做什么、为什么"，本文档回答"代码长什么样"。
> 两者冲突时以 DESIGN.md 的业务决策为准、以本文档的结构规则为准。

## 词汇约定（必须沿用，不得替换）

| 术语 | 含义 | 禁止替换为 |
|---|---|---|
| **模块** Module | 任何有接口与实现的东西：函数、类、包、跨层切片 | unit、component、service |
| **接口** Interface | 调用者必须知道的一切：类型签名、不变量、顺序约束、错误模式、必需配置、性能特征 | API、signature |
| **实现** Implementation | 模块内部 | — |
| **深度** Depth | 接口处的杠杆：调用者用少量接口知识能驱动多少行为 | 行数比 |
| **接缝** Seam | 可以不改动此处而改变行为的位置 | boundary、boundary context |
| **适配器** Adapter | 在接缝处满足接口的具体物 | — |

**核心判据**：深模块 = 小接口 + 大量行为。接口接近于实现的复杂度 = 浅模块，需要合并。

## 1. 目录结构

内部组织**按业务域切分**，而不是按技术层切分。技术层切分（`services/`、`repositories/`、`models/` 各一层）会让"改一个请假扣额度规则"需要同时打开五个目录，破坏 locality。

```
api/                      进程边界：FastAPI 应用、路由、依赖注入装配
  deps/                   请求级依赖：会话、权限上下文、事务
web/                      Next.js 应用；只通过生成的类型访问后端
domain/                   纯业务逻辑。不 import FastAPI、不 import LLM 库
  org/                    departments, job_positions
  employee/               employees, assignments, personnel_changes
  attendance/             clock events, schedules, holidays, leave, overtime
  timesheet/              projects, tasks, timesheets, entries
  payroll/                salary records, payslips
  training/               courses, enrollments
  document/               文档元数据、版本、可见性
  approval/               审批引擎（共享内核）
  notification/           通知与投递
  audit/                  审计记录写入（读取在 api 层按 compliance 角色暴露）
ai/                       AI 能力的边缘。可调用 domain，domain 绝不调用它
  providers/              LLM 供应商适配器
  agents/                 LangGraph 图与节点
  tools/                  工具注册表（只读 + 草稿）
  rag/                    解析、分块、嵌入、检索、生成
  observability/          trace 脱敏过滤器
adapters/                 在接缝处满足接口的具体物
  db/                     SQLAlchemy 仓储、RLS 上下文、迁移
  filestore/              文档与附件的卷存储
  mail/                   SMTP 发送
  queue/                  Redis 队列
  clock/                  可注入的时间源（测试用固定时钟）
workers/                  后台任务：解析、邮件、定时摘要、生效落库、快照
```

**关键约束**：`domain/` 是唯一可以承载业务规则的地方。`api/` 与 `workers/` 只做装配与调用，不写规则。

## 2. 深模块设计

### 2.1 授权内核（最重要的一个模块）

这就是 DESIGN.md §4.2 那个判定公式的代码形态。它是全系统唯一回答"这个人能不能对这个资源做这件事"的地方。

**接口（全部）：**

```
can(principal, action, resource) -> Decision
filter_for(principal, resource_kind) -> FilterSpec
apply_rls_context(session, principal) -> None
```

**实现（隐藏）：** 角色并集、密级继承、部门子树展开、显式共享、例外角色、缓存、失效通知。

**接口里必须写明的（属于接口，不属于实现）：**
- `Decision` 携带**理由**（哪条规则命中的），因为审计日志需要它，且"为什么被拒"必须是可回答的。
- `filter_for()` 的返回**不是查询构造器而是数据描述**——这是刻意选择。
- `apply_rls_context()` 必须在事务内、任何查询之前调用；顺序是接口的一部分。
- `FilterSpec` 的字段**就是判定的数据形态**，调用者翻译它时必须逐字段落地：允许的部门集合、允许的密级集合、本人的 `employee_id`（"自己的文档"这一条）、显式共享的查询主体、以及"公司文档跨部门"标志。
- **文档类资源永远不返回 `allow_all`**。它的语义是"所有行"，而所有行包含他人的个人文档——那是判定规则从不允许的。例外角色（人力资源、合规）用上面那个独立标志表达，因为它们的范围仅限公司文档。

**为什么 `filter_for()` 返回数据描述而不是查询构造器：**

同一个权限决定要被三种调用者使用——向量检索的 SQL、普通列表查询、以及测试。如果返回查询构造器，就要为每种存储各写一个构造器，且测试无法脱离数据库断言。返回纯数据（允许的部门 ID 集合、最低密级要求、是否包含个人文档）让三种调用者各自翻译，且**决定本身可以被单测直接断言**。

**`FilterSpec` 的构造权**：`FilterSpec` 没有公开构造器，只能由授权内核产出。这样"忘记过滤"在类型层面就不可能——调用者无法凭空造一个"允许一切"的过滤条件。这条属于接口的一部分，必须显式记录。

### 2.2 员工目录

**接口：**
```
resolve_assignments(employee_id, on_date) -> list[Assignment]
primary_assignment(employee_id, on_date) -> Assignment
manager_of(employee_id, on_date) -> employee_id | None
departments_of(employee_id, on_date) -> set[department_id]
visible_fields(viewer, subject) -> FieldSet
```

**实现：** 一人多职位的解析、主职位规则、部门子树展开、审批上级回退、字段级可见性。

**为什么这是深模块：** 几乎每个功能都要问"这个人的经理是谁""他能看哪些部门"。删除它，这些逻辑会散落到通知、审批、考勤、报告、AI 五个调用点，且各自的"主职位"实现会逐渐分歧——那是最难查的一类 bug。

**注意 `on_date` 参数**：所有查询都要带日期，因为职位分配有生效期。历史考勤要按当时的经理算，不能按今天的。这个参数是接口的一部分，不是可选优化。

### 2.3 审批引擎

**接口：**
```
submit(entity_type, entity_id, requester, context) -> RequestId
decide(request_id, approver, decision, comment) -> RequestState
withdraw(request_id, requester) -> RequestState
state_of(entity_type, entity_id) -> RequestState
```

四个操作，隐藏全部复杂度：两级步骤解析、审批人计算、自我审批规避、退回补正、已批准待生效、决定历史不可变。

**「已批准但未生效」归属问题**——这是本模块最容易被设计错的地方：

`personnel_changes` 的生效落库**不属于**审批引擎。审批引擎只回答"批没批"。生效是领域模块自己的定时任务读取"已批准且到期"的单据再执行。若把生效逻辑塞进引擎，引擎就必须知道每种单据的字段语义，深度立刻崩塌。

### 2.4 考勤事件模块

**接口：**
```
clock(employee_id, kind, at, source) -> Event
day_view(employee_id, business_date) -> DayRecord
recompute_day(employee_id, business_date) -> DayRecord
range_view(employee_id, from_date, to_date) -> list[DayRecord]
```

**实现（隐藏）：** 事件流追加、UTC → 马德里业务日转换、夏令时、跨午夜班次归属、异常检测、快照、更正链重算。

**接口里最关键的一条**：这些方法**只接受日期，从不接受或返回原始时间戳用于日期聚合**。时区逻辑是这个模块的内部事务——`DESIGN.md` 风险登记里"考勤业务日与 UTC 混淆"的风险，就是靠"调用者根本没有机会混淆"来消除的。

### 2.5 文档入库管道

**接口：**
```
ingest(file, metadata, permissions) -> DocumentId
status_of(document_id) -> IngestState
reprocess(document_id) -> IngestState
```

**实现：** 解析、结构化切分、父子分块、嵌入、索引建立、失败分类、重试幂等。

**判断记录**：未来若加入 OCR，应在此模块**内部**增加一个解析适配器，接口不变。接口刻意保持"一个文件进、一个状态出"的形状，正是为了容纳这类替换。

## 3. 难度评审（候选模块的取舍记录）

用删除测试逐个体检。**删除它，复杂度是消失还是散落？**

| 候选 | 删除测试结果 | 结论 |
|---|---|---|
| 授权内核 | 散落到每个查询与每个 AI 工具 | ✅ 深模块 |
| 员工目录 | 散落到通知、审批、考勤、报告、AI | ✅ 深模块 |
| 审批引擎 | 散落到四类单据各自的流转代码 | ✅ 深模块 |
| 考勤事件模块 | 散落到每个调用者的时区与事件重算逻辑 | ✅ 深模块 |
| 文档入库管道 | 散落到上传接口与 AI 层 | ✅ 深模块 |
| 单独一个"时区工具" | 复杂度消失（只是薄封装库） | ❌ 浅模块。时区是考勤模块的**内部实现** |
| 单独一个"文档访问判定" | 复杂度消失（就是授权内核的一个 action） | ❌ 浅模块。设备份实现会立刻产生两套密级规则 |
| 单独一个"通知发送器" | 部分散落 | ⚠️ 保留，但它必须依赖员工目录解析收件人，不得自己实现 |

## 4. 真正的接缝 vs 假想的接缝

规则：**一个适配器意味着假想的接缝，两个适配器才是真接缝。**

| 接缝 | 适配器 | 判定 |
|---|---|---|
| LLM 供应商 | OpenAI / DeepSeek / Claude / 测试替身 | ✅ 真接缝（异构确实存在） |
| 邮件发送 | SMTP / 内存版（测试） | ✅ 真接缝 |
| 文件存储 | 卷 / 内存版（测试） | ✅ 真接缝 |
| 时间源 | 系统时钟 / 固定时钟（测试） | ✅ 真接缝。没有它，夏令时与跨午夜无法被确定性测试 |
| 数据库 | Postgres | ⚠️ **只有生产一个适配器**。PG 不需要抽象层；把仓储写成接口会把 RLS 与 SQL 的全部价值藏在假接缝后面 |

**嵌入模型不设接缝**：维度不同不可互换，抽象它只会制造"以为可以切换"的错觉。切换嵌入模型是一条**迁移任务**，不是一个接缝（见 DESIGN.md 风险登记）。

## 5. 测试策略：真实 Postgres，禁止替身

`codebase-design` 的依赖分类在这里给出一个**硬结论**：

- 授权内核的判定逻辑依赖数据库策略（RLS），属于**无法用本地替身替代**的依赖。
- PGLite 之类的嵌替身无法承载 RLS 与 pgvector 的真实行为。用 mock 数据库测权限，等于没测。
- 因此：**权限、审计、检索过滤三类测试必须运行在真实 PostgreSQL 上**（`docker compose` 提供的测试库）。这条约束在 DESIGN.md 中已定，此处记录其**理由**：它不是偏好，是因为替身不具备被测行为。

反过来，纯计算部分（业务日归属、工作量净额计算、额度扣减、状态机流转）**应当**用固定时钟与内存依赖直接单测，不碰数据库。

**按接缝分类的测试归属：**

| 被测物 | 依赖类别 | 测试方式 |
|---|---|---|
| 业务日归属、夏令时、跨午夜 | 进程内 | 固定时钟，纯单测 |
| 额度扣减、工作日计算 | 进程内 | 纯单测 |
| 审批状态机 | 进程内 | 纯单测（引擎不碰数据库读） |
| 权限判定与过滤 | 不可替代 | 真实 Postgres + 受限角色 |
| 检索权限下推 | 不可替代 | 真实 Postgres + 真实向量 |
| LLM 回答生成 | 真外部 | 模拟适配器（不调真实 API，成本与不确定性都不可接受） |

## 6. 三条不可违反的结构约束（阻塞性规则）

这三条不是建议，是**必须写成自动化测试的**。任一条被破坏即视为构建失败。

### 约束 A：`domain/` 绝不 import `ai/`

AI 是能力边缘，业务规则是内核。依赖方向单向：`ai → domain`。

**测试**：遍历 `domain/**` 的 import 图，出现 `ai` 即失败。

这条约束保证 AI 能力的增删不会波及业务规则，也让"AI 出问题时系统仍然可用"成为一个结构性事实而非承诺。

### 约束 B：AI 模块不持有写仓储

`DESIGN.md` D22 说"Agent 永不直接写库"。**三层防御**：

1. **编译期/结构层**：`ai/**` 不 import 任何写入型仓储。测试断言 AI 可触达的工具集合中不存在写库工具。
2. **运行时**：数据库会话上下文带一个"只读"标记；只读上下文中任何 INSERT/UPDATE/DELETE 抛异常。AI 请求路径一律以只读上下文开启事务。
3. **数据库层**：为 AI 路径使用**只读数据库角色**，写操作在数据库层面被拒绝。

三层都在，是因为前两层都在应用代码里，而应用代码会被人改。第三层不依赖应用代码的正确性。

### 约束 C：查询的权限条件不可绕过

任何返回受控资源的仓储方法，其签名**必须**接收 `FilterSpec`，且有测试证明不传或伪造过滤条件无法通过类型检查。

`ai/rag` 的检索尤为关键：权限条件是**与向量检索同一个 SQL 查询**的一部分，不允许"先检索再过滤"。测试断言当用户无权访问时，越权文档**不在命中集合里**（而不是"被标记为不可见")。

## 7. 这个模块有多深？（度量方式）

不用"实现行数 / 接口行数"（那会奖励往实现里灌水）。用**杠杆**度量：

- **调用点数量**：一个实现被 N 个调用点复用 = 杠杆。
- **测试的写法**：测试是否需要知道实现细节。**接口就是测试面。**
- **改动的影响半径**：改一条规则，需要动几个文件。

自检问题：*如果一个测试在实现重构后必须修改，那它测的是实现而不是接口——这个模块的形状可能错了。*
