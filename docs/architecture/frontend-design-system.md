# 前端设计系统（规范）

> 由 `frontend-design` skill 驱动，叠加本项目的三个硬约束：**西/英双语**、**欧盟无障碍语境**、**高密度数据录入**。
> 本文档规定**系统与约束**，不设计具体页面。页面设计属于各自票据（见 §8 对照表）。

---

## 1. 设计思考：这个系统的"为什么"

| 问题 | 答案 |
|---|---|
| 要达成什么 | **工具效率**，不是转化率。用户来这里是完成一件具体的事（打卡、批假、填工时、查制度），然后离开 |
| 谁在用 | 人力资源、财务、经理、普通员工。多数每天用 1–3 分钟，经理可能连续扫几十条待批 |
| 什么场景 | 办公室桌面为主，手机用于打卡与查看。**不是**移动优先产品 |
| 内容特征 | 真实的企业数据：姓名、日期、分钟数、金额、审批意见。**没有**营销文案，没有占位图 |
| 关键约束 | 双语文本膨胀、WCAG AA、欧洲无障碍语境、表格与表单密集 |

**最重要的一条定位**：这是一个**内部工具**，不是展示型网站。前端设计的目标是让 HR 每天重复做 30 遍的操作**快而少出错**，而不是让人第一眼觉得惊艳。所有视觉决策都服从这个目标。

## 2. 设计 token（唯一来源）

Token 以 CSS 变量定义，作为西/英两套文案共用的唯一视觉来源。组件与页面**只消费 token，不写魔法值**。

### 2.1 间距：4px 基准

`4 / 8 / 12 / 16 / 24 / 32 / 48 / 64`。组件内距与外距分层使用，不混用同一档。

### 2.2 字号与排版

| 用途 | 字号 | 行高 |
|---|---|---|
| 正文（默认） | **14px** | 1.5 |
| 次要信息 | 13px | 1.45 |
| 页面标题 | 20px | 1.3 |
| 区块标题 | 16px | 1.4 |
| 表格内文字 | 13–14px | 1.4 |

**为什么正文用 14px 而不是 16px**：skill 给的区间是 14–16px。本系统要向经理展示 100 人的工时表与考勤表，16px 会让一屏只能放十几行，被迫滚动 = 效率损失。14px 仍在区间内，配合 1.5 行高保持可读。**这是有意识的取舍，不是疏忽。**

### 2.3 数字必须用等宽数字

工时、分钟数、金额、日期一律 `font-variant-numeric: tabular-nums`。

**理由**：这是 HR 系统里最实际的排版问题。工时表里 `7.5` 与 `11.5` 若用比例数字，小数点不对齐，人眼扫一列数字时会把 `11.5` 误读成 `1.5`。对齐之后整列数字的位数结构一眼可见，误读率显著下降。这不是美学偏好，是防错措施。

### 2.4 配色：克制

- 主色 **1 个**，中性色成体系（背景/边框/次要文字/主要文字至少四档），语义色用于状态。
- 语义色固定为：成功/已通过、进行中/待处理、警告/待确认、错误/已驳回、中性/已撤销。
- 语义色**成对定义**：浅底 + 深字，两套都需通过对比度检查。
- 状态**绝不只靠颜色传达**（见 §5）。

### 2.5 字体栈

西班牙语优先的系统字体栈，回退到各平台默认无衬线字体。不加载 Web 字体——内部工具不值得为字体引入渲染阻塞与体积。西语的重音符号（á é í ó ú ñ ü）与倒问号（¿ ¡）在系统字体下渲染完整，无需特殊处理。

### 2.6 动效

150–300ms，只用于反馈与状态过渡（提交中、展开收起、提示条进出）。

**必须尊重 `prefers-reduced-motion`**。**例外**：AI 回答的逐字流式输出**不属于动效**，它是内容本身的呈现方式，不受 reduced-motion 影响——这一点容易误判，需在实现时明确。

## 3. 双语布局的硬约束

这是本项目最容易被忽视、也最容易在切换语言时崩掉的地方。

### 3.1 文本膨胀

西班牙语在同一内容上通常比英语**长 15–25%**，某些 UI 词条更长。

**因此必须遵守：**

- ❌ **禁止**固定像素宽度的按钮、标签页、导航项、状态徽章
- ❌ **禁止**用省略号截断按钮与菜单项的文本来"维持布局"
- ✅ 布局按**两种语言中较长者**设计；组件用内边距驱动宽度而非固定宽度
- ✅ 表格列宽用比例或内容自适应，不用固定像素
- ✅ 交付前**两种语言各截一遍图**对比，检查是否有换行错位、截断、按钮撑破容器

### 3.2 双语文案是设计的一部分

- 文案键在西/英字典中**同时存在**，缺任一条视为缺陷（应有一条测试断言两套字典键集合一致）。
- 复数、日期、数字格式逐语言处理（西语日期格式与英语不同）。
- 语言切换即时生效，**不整页刷新、不丢失已填写的表单内容**。

## 4. 页面骨架与层级

### 4.1 应用外壳

- 左侧主导航 + 顶部栏（当前用户、通知未读、语言切换）+ 内容区。
- 导航按角色显示条目——普通员工不会看到"薪酬管理""审计日志"这类入口。**界面不出现用户无权访问的入口**，比"点了返回 403"体验好得多，也避免暴露系统结构。
- 内容区宽度上限固定，避免超宽屏上表格被拉散。

### 4.2 一次只有一个主角

每个页面明确一个主操作（提交打卡 / 批准 / 保存工时）。次要操作降级为次级按钮或文字链接。经理的审批页主角是"批准/驳回"这一对判断，其他都是辅助信息。

### 4.3 空状态、加载状态、错误状态

**三个状态都必须设计**，不能只做理想状态：

| 状态 | 设计要求 |
|---|---|
| 空 | 说明为什么空 + 下一步能做什么。例："本月暂无考勤记录——如果你今天还没打卡，点击右上角打卡" |
| 加载 | 骨架屏优先于转圈；表格用行占位。**上传与解析用进度条，且要显示当前阶段**（已上传 / 解析中 / 生成索引 / 就绪） |
| 错误 | 说明发生了什么 + 用户能做什么。统一错误码对应的西/英双语文案 + 重试入口 |

### 4.4 AI 拒答是一个必须设计的正常状态

当知识库中没有依据时，系统的回答是"未找到依据"。**这个状态必须被设计得像是系统正常工作，而不是像系统坏了**：

- 语气中性、不道歉过度
- 明确说明检索范围（"公司知识库中未找到相关内容"）
- 给出可执行的下一步（换一种问法 / 确认文档是否已上传 / 联系人力资源）
- 视觉上与正常回答可区分，但不使用"错误"红色——它不是错误

若把它渲染成红色错误框，用户会以为系统故障并来问 IT，而实际上这是设计好的正确行为。

## 5. 无障碍底线

**不是加分项。** 欧洲无障碍法案已于 2025 年 6 月生效（[参考](https://www.lexology.com/library/document.ashx?g=ea9fbe68-0163-4d00-acc9-854fa9d3498c)）；内部 HR 门户未必落入其适用范围，但在这个法域下把无障碍当可选项是不合理的风险。

| 要求 | 标准 |
|---|---|
| 对比度 | 正文 ≥ 4.5:1，大字 ≥ 3:1（浅色与深色底两套都要验） |
| 键盘 | 全部功能可纯键盘完成，焦点环可见，Tab 顺序自然，无键盘陷阱 |
| 语义化 | `header / nav / main / article / aside / footer`；每页单一 `h1`，标题层级不跳级 |
| 表单 | 每个输入都有 `<label>` 关联；错误信息与字段关联（`aria-describedby`），并给出**修正建议**而不只是"格式错误" |
| 图标按钮 | 必须有 `aria-label`（双语） |
| 状态 | **绝不只靠颜色**——出勤、审批、异常状态一律 图标 + 文字 + 颜色 三者齐备 |
| 缩放 | 不禁用缩放；文字放大到 200% 不破版 |
| 动效 | 尊重 `prefers-reduced-motion` |
| 触控 | 移动端目标 ≥ 44px |

**状态不只靠颜色**这条在本项目里格外重要：考勤状态（出勤/迟到/缺卡/休假/节假日）与审批状态（待批/通过/驳回/退回）都是密集呈现的，色觉障碍用户必须也能分辨。

## 6. 高密度数据录入的专项规则

本系统有四个"填错代价高"的界面，它们需要额外规则。

### 6.1 工时表网格（周视图）

- 单元格可直接点击输入，支持 Tab / Shift+Tab 横向移动、Enter 向下移动——**纯鼠标填一周工时是折磨**。
- 实时显示行合计、列合计、总计；超阈值时**警告但不静默截断**。
- 已锁定的周只读，视觉上明确区分，并在顶部说明"本周已锁定，如需修改请发起补充提交"。
- 补充提交时，冲销条目用不同的视觉标记，让人一眼看出哪几行是抵减。

### 6.2 考勤打卡

- 首页第一眼可见当前状态与时间，主按钮只有一个（上班 / 下班，按当前状态切换）。
- 打卡成功后给明确的即时反馈（状态变化 + 短暂提示），因为用户会立刻关掉页面。
- 打卡失败必须醒目——静默失败会导致员工以为已打卡，次日出现在异常列表里。

### 6.3 工资单批量上传（财务）

- 上传后立刻呈现两张清单：**成功归属**与**缺失**。缺失清单需要视觉上足够醒目，因为这是本界面的核心价值。
- 无法匹配的文件单独列出并给原因，不能静默丢弃。
- 覆盖同名工资单是危险操作，必须二次确认并明确写出"将覆盖 X 名员工的 Y 月工资单"。

### 6.4 审批界面（经理）

- 一次处理多条的效率优先：列表内联操作，不必逐条进详情页。
- 每条必须一眼看到关键信息：谁、什么类型、什么日期、多少天/多少小时。
- 审批意见可选，但**驳回时必填**（驳回不给理由会让员工反复提交）。
- 显示申请人的剩余额度/异常历史，让审批人有判断依据。

## 7. 响应式

| 断点 | 目标 |
|---|---|
| 320–767px | 手机：打卡、查看状态、审批、看工资单。导航折叠为抽屉。**工时表网格与批量上传在此宽度下明确降级**为"请用桌面端"提示，而不是硬挤 |
| 768–1279px | 平板：表格可横向滚动，侧栏收起 |
| ≥ 1280px | 桌面：完整布局，工时表与批量上传的主战场 |

**明确承认边界**：工时表网格与财务批量上传不做手机端适配，而是给明确的"请用桌面端"提示。硬把一个 7 列 × 20 行的网格塞进 375px 屏幕，得到的不是响应式设计，而是一个两边都难用的界面。

- [ ] 正文对比度 ≥ 4.5:1（浅底与深底都验过）

- [ ] 正文 14–16px、行高 1.5+，数字用等宽数字
- [ ] 间距取自 4px 基准 token，无魔法值
- [ ] 默认 / hover / focus / active / disabled / 错误 六态齐全
- [ ] 表单有 label、校验、错误提示与修正建议
- [ ] **空状态 / 加载状态 / 错误状态都已设计**
